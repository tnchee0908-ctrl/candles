# Свечная мастерская: учёт производства и ИИ-ассистент

Мини-система учёта склада и производства для вымышленной мастерской ароматических свечей. Поверх неё работает ИИ-ассистент, который отвечает на вопросы по данным, считает в Code Interpreter и готовит действия, выполняемые только после подтверждения пользователя.

## Запуск

```bash
cp .env.example .env        # вставьте OPENAI_API_KEY (без ключа работает всё, кроме чата)
docker compose up --build
```

| Что | Адрес |
|---|---|
| Интерфейс | http://localhost:8080 |
| OpenAPI (Swagger) | http://localhost:8000/docs |
| Мок курсов валют | http://localhost:8101/docs |
| Мок маркировки (принятые отчёты и статистика) | http://localhost:8102/reports |

`docker compose up` поднимает PostgreSQL, Redis, оба мока, бэкенд (сам применяет миграции Alembic и заливает демо-данные), фоновый воркер arq и фронтенд (nginx).

## Демо-данные

Создаются через тот же сервисный слой, поэтому FIFO, резервы и журнал настоящие. Даты отсчитываются от сегодняшнего дня, так что вопросы про «эту неделю» работают в любой день.

* 13 материалов, 3 рецепта («Лаванда», «Ваниль», «Кедр»), 4 поставщика.
* Поступления в RUB, USD и EUR за ~100 дней. Одна поставка в евро пришла в субботу, её себестоимость посчитана по курсу пятницы.
* Партия «Брак», партия «На проверке», комментарий с ПДн («Принял Петров И. С.») и партия с промпт-инъекцией в комментарии.
* Поставщик заведён как «ООО Восковой двор», вторая поставка оформлена как «Восковой двор, ООО». Система узнаёт, что это тот же поставщик.
* 13 завершённых заданий за 3 месяца (с перерасходом и экономией; это данные для графиков), одно задание «В работе», одно запланированное без дефицита, **одно с дефицитом** («Ваниль», 150 шт: кокосового воска хватает на четверть) и черновик на следующую неделю.
* Последний отчёт в маркировку ещё не отправлен. После запуска видно, как воркер пробивается через 500-е ответы мока (страница «Маркировка» или карточка задания).

## Архитектура

```
frontend (React + TS + Tailwind, nginx)  ──/api──►  backend (FastAPI)
                                                     ├─ api/          тонкие роутеры
                                                     ├─ services/     ВСЯ бизнес-логика: партии, FIFO, задания, права, журнал
                                                     ├─ assistant/    чат: LLM-роутер, инструменты, ПДн, память, песочница
                                                     └─ prompts/      промпты отдельными файлами
                         PostgreSQL ◄──── Alembic-миграции
                         Redis ◄──── worker (arq): отправка в маркировку, повторы
                         mocks/rates.py, mocks/marking.py: внешние сервисы
```

**Главное правило:** кнопка в интерфейсе и инструмент ассистента вызывают одну и ту же функцию сервиса. Например, «Создать и запланировать» в форме и «Подтвердить» под ответом ассистента обе вызывают `orders.create_and_plan`.

## Модели

* **Основная: `gpt-4.1-mini`.** Хорошо вызывает инструменты (в том числе несколько подряд), поддерживает Code Interpreter в Responses API, быстро отдаёт первый токен в стриме и стоит недорого, что важно при лимите ключа. Модель без reasoning, поэтому ответ начинает печататься сразу.
* **Запасная: `gpt-4o-mini`.** Другое семейство: если у основной проблемы с лимитом или ёмкостью, запасная, скорее всего, жива. Тоже умеет tool calling и Code Interpreter.
* **Судья в эталонном прогоне: `gpt-4.1-mini`.** Оценивает только по рубрике и эталонным числам.

Все три задаются переменными окружения (`LLM_PRIMARY_MODEL`, `LLM_FALLBACK_MODEL`, `LLM_JUDGE_MODEL`).

## Как устроен ассистент

Путь запроса: вопрос → **маскирование ПДн** → модель (основная, при сбое запасная) ⇄ **инструменты сервисного слоя** и Code Interpreter → **обратная замена псевдонимов** → SSE-стрим пользователю.

* **Стриминг.** `POST /api/chat/conversations/{id}/messages` возвращает Server-Sent Events: `start`, `delta`, `tool`, `code`, `action`, `file`, `model`, `done`. Кнопка «Остановить» обрывает поток и вызывает `/stop`. Ход выполняется в отдельной задаче, поэтому остановка или обрыв сохраняют уже напечатанное со статусом `interrupted`. Под ответом видны модель (с пометкой «запасная», если ответила она), вызванные инструменты и раскрываемый код Code Interpreter.
* **Инструменты** (`app/assistant/tools.py`). Чтение: `get_material_stock`, `get_shortages`, `get_batch_history`, `get_order_cost`, `list_orders`, `list_recipes`, `find_batches`, `get_currency_rate`. Действие: `propose_production_order`. Ещё есть `remember_fact` и `export_dataset`. Аргументы валидируются Pydantic-моделями с `extra="forbid"` и ограничениями. Ошибка валидации, прав или бизнес-правила возвращается модели текстом, чат не падает. SQL модель не пишет.
* **Действия только через подтверждение.** `propose_production_order` проверяет права и считает превью (что зарезервируется, какой будет дефицит), но в учёт ничего не пишет. Создаётся только `PendingAction`. Данные меняются после нажатия «Подтвердить» (`/api/chat/actions/{id}/confirm`): подтвердить можно только своё действие и только один раз.
* **Code Interpreter.** Для диалога создаётся контейнер OpenAI. Бэкенд кладёт туда CSV, собранный сервисным слоем, с учётом прав (например, без себестоимости для кладовщика) и уже с псевдонимами (`export_dataset`). Модель получает только нужный набор, а не всю базу. Загруженные пользователем CSV/XLSX тоже маскируются перед отправкой в песочницу. Файлы, созданные кодом (PNG, CSV, XLSX), скачиваются в БД и показываются в чате; в CSV/XLSX настоящие имена возвращаются обратно.
* **Честные ответы.** Системный промпт (`prompts/system.md`) требует брать числа только из инструментов и говорить «данных нет». Комментарии к партиям приходят в поле `comment_untrusted_data`. Главная защита от инъекций при этом структурная, а не промптовая: у ассистента нет инструментов отмены и удаления, единственное действие требует подтверждения человеком, и права проверяет сервис.
* **Надёжность** (`app/assistant/llm/`). `LLMProvider` — интерфейс с одним методом `stream()`, `FallbackLLM` перебирает провайдеров. 429, 5xx, таймаут и обрыв соединения **до первого токена** переключают на запасную модель. 4xx из-за самого запроса не повторяется. Если стрим оборвался **после** начала, ответ сохраняется как прерванный (повтор запасной моделью начал бы ответ заново). У каждого вызова таймаут `asyncio.timeout` поверх таймаута HTTP-клиента; ретраи SDK отключены, ими управляет роутер. Чтобы добавить другого провайдера, достаточно реализовать `stream()`.
* **Персональные данные** (`app/assistant/pii.py`). ФИО сотрудников и названия поставщиков заменяются на `PERSON_n` и `SUPPLIER_n`. Псевдоним постоянный (хранится в БД) и находится при любом написании: «ООО Восковой двор», «Восковой двор, ООО», «у Воскового двора», «Петров Иван», «Петрову И.», «И. С. Петров», «Иван Сергеевич». Используются основа слова плюс падежные окончания, инициалы и правовые формы. Псевдонимы латиницей выбраны намеренно: модель их не склоняет, и обратная замена надёжна. Замена в стриме учитывает, что псевдоним может прийти разрезанным на части. В логах пишутся только имя инструмента и маскированные аргументы.
* **Память.** Ассистент сохраняет факты инструментом `remember_fact`, они попадают в системный промпт только этого пользователя. Все запросы фильтруются по `user_id`, удалить можно только свой факт. Страница «Память» показывает список, позволяет удалить один факт или очистить всё.

## Учётное ядро: решения

* **Деньги и количества** хранятся как `numeric` в БД и `Decimal` в Python, в JSON отдаются строками (точность не теряется), на фронте только форматируются.
* **Номера документов** (`П-00001`, `З-00001`, `ПСТ-00001`) выдают последовательности PostgreSQL.
* **Себестоимость партии** = цена × курс на дату поступления, хранится в рублях за единицу. Курс берётся из мок-сервиса; если на дату его нет (выходной), берётся ближайший предыдущий, но не дальше 14 дней. Курсы кэшируются в таблице `currency_rates`. В карточке партии видно, за какую дату взят курс.
* **Статусы партии:** «На проверке» → «Принята» / «Брак», обратных переходов нет. Резервируются только принятые партии с остатком. *Допущение:* найденный позже брак принятой партии оформляется отдельной операцией списания (не реализована).
* **Жизненный цикл задания:** Черновик → Запланировано → В работе → Завершено; отмена возможна только из «Черновика» и «Запланировано». Повторное планирование запланированного задания дорезервирует недостающее (кнопка «Дорезервировать»).
* **FIFO и параллельность.** При планировании партии материала блокируются `SELECT … FOR UPDATE` в порядке `received_date, id`, материалы обрабатываются по `id`, поэтому два одновременных запроса выстраиваются в очередь и не берут один остаток, а взаимоблокировок нет. Страховка в схеме: `CHECK (reserved_qty <= remaining_qty)` и `CHECK (reserved_qty >= 0)`. При нехватке выполняется частичный резерв, дефицит показывается, запуск с дефицитом запрещён.
* **Завершение.** Резерв списывается по FIFO в пределах факта, экономия остаётся в партиях, перерасход досписывается из свободного остатка по FIFO. Если свободного нет, ошибка звучит так: «Не хватает 2,5 кг «Воск соевый»…».
* **«Светофор»:** зелёный — резерв полный, жёлтый — частичный, красный — нулевой. После запуска все компоненты считаются зелёными.
* **Журнал изменений** пишется в той же транзакции, что и изменение: ФИО, время, снимки «было» и «стало», пометка «через ассистента».
* **Маркировка: transactional outbox.** Отчёт создаётся в одной транзакции с завершением задания, само завершение сервис не ждёт. Воркер arq отправляет отчёт сразу (задача в очереди) и подбирает просроченные каждые 5 секунд (cron). Повторы идут с экспоненциальной паузой и разбросом ±20%: 2 → 4 → 8 … до 300 с, максимум 8 попыток, затем статус «Не отправлен» и ручная кнопка «Повторить». `Idempotency-Key` зависит только от задания, поэтому повтор после потерянного ответа не создаёт дубль (мок это проверяет). Таймаут клиента 5 с: ответ мока через 10 с считается неудачной попыткой. Журнал попыток виден в UI. 4xx (кроме 408 и 429) не повторяется.
* **Ошибки** приходят пользователю текстом: доменные исключения превращаются в `400/403/404/409` с сообщением, ошибки валидации — в «Проверьте данные — …», неожиданные — в аккуратную 500 без трассировки.

## Допущения

* Цех задания — 1, 2 или 3. Неделя считается с понедельника.
* «Дефицит по заданиям за период» сравнивает незарезервированную потребность незапущенных заданий (черновики и запланированные) со **свободным остатком сейчас**. Партии «На проверке» показываются отдельно, но не учитываются.
* Себестоимость незавершённого задания оценивается по текущему резерву, незарезервированная часть явно помечена как «без цены». У завершённого — по фактическому списанию.
* Средняя себестоимость материала для расчётов «что если» — средневзвешенная по количеству всех принятых партий.
* Ассистент не умеет отменять, запускать и принимать: это делается кнопками. Единственное действие — создать и запланировать задание.
* В песочницу загружаются CSV, XLSX, TXT, TSV и JSON до 5 МБ.
* Курсы для сида считаются той же функцией, что в моке, но без сети, чтобы порядок старта контейнеров не влиял на заливку данных.

## Что не успели и что бы улучшил

* **Отчёт эталонного прогона и видео** появятся после получения ключа OpenAI: скрипт и 14 вопросов готовы, запуск — одна команда (см. выше). Прогон через настоящую модель без ключа выполнить нельзя.
* Подписи на PNG-графиках остаются с псевдонимами (картинку нельзя «размаскировать»). Графикам по материалам и неделям это не мешает, а для графиков по поставщикам нужна расшифровка псевдонимов в UI под картинкой.
* Остановка хода хранится в памяти процесса (`ACTIVE_TURNS`). При нескольких воркерах uvicorn её нужно перенести в Redis pub/sub.
* Нет списания брака у уже принятой партии, редактирования рецептов из UI и ручного ввода курса.
* Дополнительные задачи (pgvector, голос, Excel-экспорт, Playwright + CI) не делались, приоритет был у основных частей.
