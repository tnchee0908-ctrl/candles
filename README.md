# Свечная мастерская: учёт производства и ИИ-ассистент

Мини-система учёта склада и производства для вымышленной мастерской ароматических свечей. Поверх неё работает ИИ-ассистент, который отвечает на вопросы по данным, считает в Code Interpreter и готовит действия, выполняемые только после подтверждения пользователя.

**Демо:** https://candles888.shop — логины те же, что в таблице ниже, демо-пользователи есть прямо на странице входа.

## Запуск

```bash
cp .env.example .env        # вставьте OPENAI_API_KEY (без ключа работает всё, кроме чата)
docker compose up --build
```

Порты публикуются только на `127.0.0.1`: снаружи машины к API и мокам не подключиться.

| Что | Адрес |
|---|---|
| Интерфейс | http://localhost:8080 |
| OpenAPI (Swagger) | http://localhost:8000/docs |
| Мок курсов валют | http://localhost:8101/docs |
| Мок маркировки (принятые отчёты и статистика) | http://localhost:8102/reports |

`docker compose up` поднимает PostgreSQL, Redis, оба мока, бэкенд (сам применяет миграции Alembic и заливает демо-данные), фоновый воркер arq и фронтенд (nginx). Образ бэкенда собирается один раз и используется API, воркером и моками; у всех сервисов `restart: unless-stopped` — упавший воркер поднимется сам.

### Тесты, линтеры, эталонный прогон

```bash
docker compose run --rm --build tests                 # ruff + тесты на настоящем PostgreSQL, без сети
docker compose run --rm --build tests sh scripts/mutants.sh   # сила тестов: 14 реалистичных ошибок, все должны быть пойманы
docker compose run --rm tests python scripts/fuzz_api.py          # фаззинг всех эндпоинтов из OpenAPI (стенд поднят)
docker compose run --rm tests python scripts/live_assistant.py file_injection memory_style chart stop  # ассистент вживую
cd frontend && npm install && npm run lint && npm run build
docker compose exec backend python -m eval.run_eval                 # эталонные вопросы, нужен OPENAI_API_KEY
docker compose exec backend python -m eval.run_eval --model both    # тот же набор на основной и на запасной модели
```

Тесты живут в отдельной стадии образа (`target: test`): в рабочий образ не попадают ни `tests/`, ни pytest/ruff. Отчёт прогона сохраняется в `backend/eval/reports/latest.md` (папка примонтирована из контейнера).

`scripts/mutants.sh` вносит в копию кода по одной реалистичной ошибке (снять блокировку, не перечитать партии после `FOR UPDATE`, перезаписать резерв вместо добавления, другое округление денег, не проверять основание факта памяти, подставлять имена в ссылки, не переключаться при 404 модели и т.д.) и проверяет, что набор тестов падает. Сейчас пойманы все 14. `scripts/fuzz_api.py` берёт все операции из OpenAPI и шлёт ~5000 запросов (без токена, с мусорным токеном и под тремя ролями; пустые, огромные, отрицательные значения, NUL, даты 0001-01-01 и 9999-12-31, не тот тип): ни одного 500, ответ всегда JSON, текст ошибки по-русски.

**Последний прогон** ([отчёт](backend/eval/reports/latest.md), `--model both`, 18.10.2026, на демо-данных стенда): **основная модель — 14 из 14** по машинным проверкам и 14 из 14 «pass» у судьи; **запасная — 13 из 14** и 12 из 14. Промахи запасной настоящие: в расчёте «что если» она не стала выгружать данные в Code Interpreter, в двух ответах объяснила причину неполно. Машинные проверки стали строже (числа сверяются с данными инструментов, заявления о действиях ловятся по корню слова), судья — другая модель (`gpt-4o`) и видит результаты инструментов. В наборе есть вопросы без ответа в данных (курс биткоина, продажи), Code Interpreter (график, расчёт «что если») и три промпт-инъекции: от пользователя, в комментарии к партии и в загруженном файле (`injection_file`, добавлен после повторной самопроверки: на нём основная модель открывает файл и не выполняет инструкцию, запасная честно отвечает, что открыть файл не может).

## Развёртывание на сервере

Для сервера есть `docker-compose.prod.yml`. Перед сайтом стоит Caddy, он сам получает и продлевает HTTPS-сертификат. Наружу открыты только порты 80 и 443: база, Redis, бэкенд и моки доступны лишь внутри сети Docker. Контейнеры перезапускаются сами. У ассистента включены лимиты (по умолчанию 30 сообщений в час на пользователя и 300 в сутки на всех), чтобы публичный стенд не израсходовал бюджет ключа.

1. **Сервер:** VPS с Ubuntu 24.04, от 2 ГБ памяти. **Только в стране, где работает OpenAI API**, например в ЕС: из России API отвечает отказом (ассистент тогда покажет понятную ошибку).
2. **Домен:** A-запись в DNS указывает на IP сервера.
3. **На сервере:**

```bash
curl -fsSL https://get.docker.com | sh
git clone <ссылка на репозиторий> candles && cd candles
cp .env.example .env    # заполнить OPENAI_API_KEY, DOMAIN и JWT_SECRET (openssl rand -hex 32), без JWT_SECRET не запустится
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Обновление: `git pull`, затем та же команда `up -d --build`.

## Демо-данные

Создаются через тот же сервисный слой, поэтому FIFO, резервы и журнал настоящие. Даты отсчитываются от сегодняшнего дня по Москве, а задание с дефицитом всегда попадает в текущую неделю (в воскресенье — на сегодня), так что вопросы про «эту неделю» работают в любой день, включая выходные. Сид атомарный: если он упадёт посередине, в базе не останется половины данных.

* 13 материалов, 3 рецепта («Лаванда», «Ваниль», «Кедр»), 4 поставщика.
* Поступления в RUB, USD и EUR за ~100 дней. Одна поставка в евро пришла в субботу, её себестоимость посчитана по курсу пятницы.
* Партия «Брак», партия «На проверке», комментарий с ПДн («Принял Петров И. С.») и партия с промпт-инъекцией в комментарии.
* Поставщик заведён как «ООО Восковой двор», вторая поставка оформлена как «Восковой двор, ООО». Система узнаёт, что это тот же поставщик. У «Aroma Trade GmbH» задано русское написание «Арома Трейд» (`suppliers.aliases`).
* 13 завершённых заданий за 3 месяца (с перерасходом и экономией; это данные для графиков), одно задание «В работе», одно запланированное без дефицита, **одно с дефицитом** («Ваниль», 150 шт: кокосового воска хватает на четверть) и черновик на следующую неделю.
* Отчёты в маркировку по прошлым заданиям сид сам не «отправляет»: при старте их отправляет настоящий воркер, и в журнале попыток только реальные ответы мока. Видно, как он пробивается через 500-е (страница «Маркировка» или карточка задания).

## Архитектура

```
frontend (React + TS + Tailwind, nginx)  ──/api──►  backend (FastAPI)
  ├─ components/ui/      дизайн-система: кнопки, поля, таблицы, бейджи, «светофор», таймлайн
  ├─ components/chat/    компоненты ассистента: сообщения, карточка подтверждения, код, файлы
  ├─ styles/tokens.css   цвета как CSS-переменные (тёмную тему можно добавить без правки классов)
  └─ pages/              экраны: данные — из API, вёрстка — из компонентов
                                                     ├─ api/          тонкие роутеры
                                                     ├─ services/     ВСЯ бизнес-логика: партии, FIFO, задания, права, журнал
                                                     ├─ assistant/    чат: LLM-роутер, инструменты, ПДн, память, песочница
                                                     └─ prompts/      промпты отдельными файлами
                         PostgreSQL ◄──── Alembic-миграции
                         Redis ◄──── worker (arq): отправка в маркировку, повторы
                         mocks/rates.py, mocks/marking.py: внешние сервисы
```

**Главное правило:** кнопка в интерфейсе и инструмент ассистента вызывают одну и ту же функцию сервиса. Например, «Создать и запланировать» в форме и «Подтвердить» под ответом ассистента обе вызывают `orders.create_and_plan`.

## Модели

* **Основная: `gpt-4.1-mini`.** Хорошо вызывает инструменты (в том числе несколько подряд), поддерживает Code Interpreter в Responses API, быстро отдаёт первый токен в стриме и стоит недорого, что важно при лимите ключа. Модель без reasoning, поэтому ответ начинает печататься сразу.
* **Запасная: `gpt-4o-mini`.** Другое семейство: если у основной проблемы с лимитом или ёмкостью, запасная, скорее всего, жива. Тоже умеет tool calling и Code Interpreter.
* **Судья в эталонном прогоне: `gpt-4o`.** Другая модель, чем та, что отвечает, — модель не оценивает сама себя. Оценивает только по рубрике и эталонным числам.

Все три задаются переменными окружения (`LLM_PRIMARY_MODEL`, `LLM_FALLBACK_MODEL`, `LLM_JUDGE_MODEL`). Температура 0,2: ответы по учётным данным должны быть повторяемыми, а не «творческими». Так расчёты и формулировки меньше меняются от прогона к прогону.

Интерфейс: собственная дизайн-система на Tailwind (токены через CSS-переменные), иконки lucide-react, шрифты IBM Plex Sans/Mono подключены локально через @fontsource — без внешних запросов. Журнал изменений показывается человеческим языком («Статус: Черновик → Запланировано»), а не сырыми полями.

Промпты лежат отдельными файлами в `backend/app/prompts/`: `system.md` (ассистент), `tools.yaml` (описания инструментов и их аргументов), `notes.yaml` (служебные пометки в результатах инструментов), `judge.md` (судья). В коде инструментов — только типы и ограничения аргументов.

## Как устроен ассистент

Путь запроса: вопрос → **маскирование ПДн** → модель (основная, при сбое запасная) ⇄ **инструменты сервисного слоя** и Code Interpreter → **обратная замена псевдонимов** → SSE-стрим пользователю.

* **Стриминг.** `POST /api/chat/conversations/{id}/messages` возвращает Server-Sent Events: `start`, `delta`, `tool`, `code`, `action`, `file`, `model`, `done`. Кнопка «Остановить» обрывает поток и вызывает `/stop`. Ход выполняется в отдельной задаче, поэтому остановка или обрыв сохраняют уже напечатанное со статусом `interrupted`. Под ответом видны все модели, которые отвечали на шагах хода (пометка «запасная» — только если она действительно ответила), вызванные инструменты и раскрываемый код Code Interpreter (с пометкой ошибки, если Python упал).
* **Инструменты** (`app/assistant/tools.py`). Чтение: `get_material_stock`, `get_shortages`, `get_batch_history`, `get_order_cost`, `list_orders`, `list_recipes`, `find_batches`, `get_currency_rate`. Действие: `propose_production_order`. Ещё есть `remember_fact` и `export_dataset`. Аргументы валидируются Pydantic-моделями с `extra="forbid"` и ограничениями. Ошибка валидации, прав или бизнес-правила возвращается модели текстом, чат не падает. SQL модель не пишет.
* **Действия только через подтверждение.** `propose_production_order` проверяет права и считает превью (что зарезервируется, какой будет дефицит), но в учёт ничего не пишет. Создаётся только `PendingAction`. Данные меняются после нажатия «Подтвердить» (`/api/chat/actions/{id}/confirm`): подтвердить можно только своё действие, только один раз и только в течение 30 минут — потом предложение «устарело» (остатки могли измениться).
* **Code Interpreter.** Для диалога создаётся контейнер OpenAI. Бэкенд кладёт туда CSV, собранный сервисным слоем, с учётом прав (например, без себестоимости для кладовщика) и уже с псевдонимами (`export_dataset`). Модель получает только нужный набор, а не всю базу. Загруженный пользователем файл в песочницу **собирается заново по белому списку** (`app/assistant/uploads.py`): из XLSX переносятся только значения ячеек — свойства документа (автор, кто изменил), комментарии и их авторы, колонтитулы в новый файл просто не попадают; CSV/TSV маскируются по ячейкам (кавычки и разделители не ломаются), кодировка определяется с учётом UTF-16. Имя файла в контейнере — `upload_<id>.xlsx`, модели передаётся маскированное исходное имя. XLSX проверяется на «zip-бомбу» (не больше 50 МБ после распаковки) ещё при загрузке. Выгрузка `export_dataset` — до 5000 строк, а если данных больше, модель получает пометку и говорит, что данные неполные. Файлы, созданные кодом (PNG, CSV, XLSX), скачиваются в БД и показываются в чате; в CSV/XLSX настоящие имена возвращаются обратно. Служебный JSON-описатель графика, который Code Interpreter создаёт сам, отфильтровывается. Картинка, перехваченная из незакрытой фигуры (`cfile_….png`), получает имя «график_N.png», а если модель сохранила график и сама, отбрасывается как дубль. Ссылки модели вида `sandbox:/mnt/data/…` в тексте превращаются в кнопку скачивания.
* **Честные ответы.** Системный промпт (`prompts/system.md`) требует брать числа только из инструментов и говорить «данных нет». Пересчёт в другую валюту делает инструмент (`get_currency_rate` с `amounts_rub`, Decimal), а не модель в уме. Комментарии к партиям приходят в поле `comment_untrusted_data`. Главная защита от инъекций при этом структурная, а не промптовая: у ассистента нет инструментов отмены и удаления, единственное действие требует подтверждения человеком, и права проверяет сервис.
* **Надёжность** (`app/assistant/llm/`). `LLMProvider` — интерфейс с одним методом `stream()`, `FallbackLLM` перебирает провайдеров. 429, 5xx, таймаут и обрыв соединения **до первого токена** переключают на запасную модель. Так же — если недоступна сама модель: 404 `model_not_found`, «нет доступа к модели», неподдерживаемый параметр (граница: 404 у нас всегда про модель, 400/403 — когда OpenAI прямо говорит о модели). 4xx из-за самого запроса (например, слишком длинный контекст) не повторяется. Если стрим оборвался **после** начала, ответ сохраняется как прерванный (повтор запасной моделью начал бы ответ заново). Таймаутов два: на паузу между событиями стрима (`LLM_IDLE_TIMEOUT_S`, 90 с — события прогресса Code Interpreter её сбрасывают, поэтому долгий расчёт не обрывается) и потолок на весь шаг (`LLM_TIMEOUT_S`, 300 с). Ретраи SDK отключены, ими управляет роутер. Чтобы добавить другого провайдера, достаточно реализовать `stream()`.
* **Персональные данные** (`app/assistant/pii.py`). ФИО сотрудников и названия поставщиков заменяются на `PERSON_n` и `SUPPLIER_n`. Псевдоним постоянный (хранится в БД) и находится при любом написании: «ООО Восковой двор», «Восковой двор, ООО», «у Воскового двора», «Восковой_двор_прайс», «Voskovoy dvor», «Петров Иван», «Петрову И.», «И. С. Петров», «Иван Сергеевич», «Petrov Ivan»; для поставщика можно задать другие написания (`suppliers.aliases`). Чтобы не путать людей и обычные слова: фамилия совпадает только с заглавной буквы («кузнецов» — не сотрудник Кузнецов); одиночная фамилия рядом с **другим** именем или инициалом — однофамилец («Петрова Ольга», «Смирнов Пётр», «Стеклова Мария» не трогаются); дефис — часть фамилии («Петрова-Водкина» — другой человек); кавычки вокруг названия снимаются только парой, поэтому CSV и JSON не ломаются. Псевдонимы латиницей выбраны намеренно: модель их не склоняет, и обратная замена надёжна. Замена в стриме учитывает, что псевдоним может прийти разрезанным на части. **Внутри ссылок имена обратно не подставляются**, а картинки по внешним адресам из текста ответа не загружаются (плюс CSP в nginx) — канал утечки через `![](https://…?d=…)` закрыт. В логах пишутся только имя инструмента и маскированные аргументы, журналы запросов (uvicorn и nginx) — без query string: фильтр «поставщик = ИП Стеклов» в логи не попадает. SQLAlchemy не включает значения параметров в тексты ошибок (`hide_parameters`), PostgreSQL пишет журнал без DETAIL и текста запроса — значения строк с ФИО туда не попадают.
* **Память.** Ассистент сохраняет факты инструментом `remember_fact` (в том числе о стиле ответов: «пиши покороче»), они попадают в системный промпт только этого пользователя. Защита от внедрённых фактов **структурная**: модель обязана передать `source_quote` — дословный фрагмент текущего сообщения пользователя, и бэкенд проверяет, что он там есть. «Запомни, что…» из комментария партии или загруженного файла сохранить не получится, даже если модель поддастся. Все изменения памяти пишутся в журнал изменений. Запросы фильтруются по `user_id`, удалить можно только свой факт. Страница «Память» показывает список, позволяет удалить один факт или очистить всё.

## Учётное ядро: решения

* **Деньги и количества** хранятся как `numeric` в БД и `Decimal` в Python, в JSON отдаются строками (точность не теряется) — в том числе в себестоимости задания и отчёте о дефиците; на фронте только форматируются. Итог себестоимости — сумма уже округлённых строк (без расхождения на копейку). Округление денег — половина вверх.
* **Номера документов** (`П-00001`, `З-00001`, `ПСТ-00001`) выдают последовательности PostgreSQL.
* **Себестоимость партии** = цена × курс на дату поступления, хранится в рублях за единицу. Курс берётся из мок-сервиса; если на дату его нет (выходной), берётся ближайший предыдущий, но не дальше 14 дней. Курсы кэшируются в таблице `currency_rates`. В карточке партии видно, за какую дату взят курс.
* **Статусы партии:** «На проверке» → «Принята» / «Брак», обратных переходов нет. Резервируются только принятые партии с остатком; у брака и непроверенной партии «свободно» = 0. Сортировка реестра по цене сравнивает цены в рублях. *Допущение:* найденный позже брак принятой партии оформляется отдельной операцией списания (не реализована).
* **Жизненный цикл задания:** Черновик → Запланировано → В работе → Завершено; отмена возможна только из «Черновика» и «Запланировано». Повторное планирование запланированного задания дорезервирует недостающее (кнопка «Дорезервировать»). Черновик с прошедшей плановой датой не планируется — его нужно пересоздать на актуальную дату.
* **Даты** считаются по Москве (`common.today()`, во фронте `businessDate()`), а не по UTC контейнера: с 00:00 до 03:00 МСК «сегодня» — уже сегодня.
* **FIFO и параллельность.** При планировании партии материала блокируются `SELECT … FOR UPDATE` в порядке `received_date, id`, материалы обрабатываются по `id`, поэтому два одновременных запроса выстраиваются в очередь и не берут один остаток, а взаимоблокировок нет. Страховка в схеме: `CHECK (reserved_qty <= remaining_qty)` и `CHECK (reserved_qty >= 0)`. При нехватке выполняется частичный резерв, дефицит показывается, запуск с дефицитом запрещён.
* **Запуск = выдача в цех** (как в схеме ТЗ): весь резерв задания списывается из партий, остаток склада уменьшается, в карточке — «Выдано в цех из партий». Себестоимость задания «В работе» считается по выданному.
* **Завершение** сверяет факт с выданным: перерасход досписывается из свободного остатка по FIFO, экономия возвращается в те партии, из которых выдавали (сначала в самые новые, чтобы старые продолжали уходить первыми). Факт по материалам в штуках — только целый. Если свободного остатка на перерасход нет, ошибка звучит так: «Не хватает 2,5 кг «Воск соевый»…». *Осознанное ограничение:* перерасход не забирает материал, зарезервированный под другие незапущенные задания, — тихо отнять резерв у чужого задания хуже, чем остановиться. Решение за человеком: снять или перенести чужой резерв либо оформить поступление.
* **«Светофор»:** зелёный — резерв полный, жёлтый — частичный, красный — нулевой. После запуска все компоненты считаются зелёными.
* **Журнал изменений** пишется в той же транзакции, что и изменение: ФИО, время, снимки «было» и «стало», пометка «через ассистента».
* **Маркировка: transactional outbox.** Отчёт создаётся в одной транзакции с завершением задания, само завершение сервис не ждёт. Воркер arq отправляет отчёт сразу (задача в очереди) и подбирает просроченные каждые 5 секунд (cron в :00, :05, :10 …; проверено по журналу воркера, строки arq больше не дублируются). HTTP-запрос к сервису идёт **вне транзакции**: отчёт сначала «арендуется» короткой транзакцией (сдвигается время следующей попытки), затем отправляется, затем результат пишется второй транзакцией — строка не заблокирована, пока ждём ответа. Повторы идут с экспоненциальной паузой и разбросом ±20%: 2 → 4 → 8 … с, но не реже раза в час; повторы идут около суток (36 попыток), затем статус «Не отправлен» и ручная кнопка «Повторить» — она запускает новый полный цикл попыток (журнал нумеруется дальше). Если воркер упал (например, пропал Redis), его перезапустит Docker (`restart: unless-stopped`), и он подберёт все неотправленные отчёты. Журнал отправок в карточке задания виден тем же ролям, что и страница «Маркировка». `Idempotency-Key` зависит только от задания, поэтому повтор после потерянного ответа не создаёт дубль (мок это проверяет). Таймаут клиента 5 с: ответ мока через 10 с считается неудачной попыткой. Журнал попыток виден в UI. 4xx (кроме 408 и 429) не повторяется.
* **Ошибки** приходят пользователю текстом (`app/web.py`): доменные исключения — `400/403/404/409` с сообщением; ошибки валидации — «Проверьте данные — цена: должно быть не больше 100000000» (русские тексты и названия полей); 404/405 самого фреймворка — тоже по-русски. Идентификаторы ограничены диапазоном `integer` PostgreSQL, цены и количества — так, чтобы себестоимость не переполнила колонку, даты — 2000…2100 годами (поступление — не старше 5 лет, плановая дата — не дальше 2 лет вперёд); NUL-байт в адресе или JSON отклоняется до бизнес-логики. Если некорректное значение всё же дошло до базы, ответ — 400 с текстом, а не 500. Тест обходит все маршруты с id. Ошибки самого nginx (файл больше 6 МБ, бэкенд перезапускается) — тоже JSON с текстом, а фронтенд на обрыв связи пишет «Нет связи с сервером», а не «Failed to fetch».
* **Безопасность стенда.** Пустой или известный из примеров `JWT_SECRET` не используется — бэкенд генерирует случайный (токен, подписанный «change-me-in-production», отклоняется); на сервере секрет обязателен. После 5 неудачных входов за 15 минут с одного адреса для логина — пауза (считаем по паре «логин + адрес», чтобы никто не мог заблокировать вход демо-пользователю). nginx отдаёт CSP, `nosniff`, `no-referrer`.

## Допущения

* Цех задания — 1, 2 или 3. Неделя считается с понедельника.
* «Дефицит по заданиям за период» сравнивает незарезервированную потребность незапущенных заданий (черновики и запланированные) со **свободным остатком сейчас**. Партии «На проверке» показываются отдельно, но не учитываются.
* Себестоимость незапущенного задания оценивается по текущему резерву, незарезервированная часть явно помечена как «без цены». У задания «В работе» — по выданному в цех, у завершённого — по фактическому списанию.
* Средняя себестоимость материала для расчётов «что если» — средневзвешенная по количеству всех принятых партий.
* Ассистент не умеет отменять, запускать и принимать: это делается кнопками. Единственное действие — создать и запланировать задание.
* В песочницу загружаются CSV, XLSX, TXT, TSV и JSON до 5 МБ.
* Курсы для сида считаются той же функцией, что в моке, но без сети, чтобы порядок старта контейнеров не влиял на заливку данных.

## Что не успели и что бы улучшил

* Подписи на PNG-графиках остаются с псевдонимами (картинку нельзя «размаскировать»). Графикам по материалам и неделям это не мешает, а для графиков по поставщикам нужна расшифровка псевдонимов в UI под картинкой.
* Запасная модель (`gpt-4o-mini`) слабее в Code Interpreter: бывает, что не открывает загруженный файл, а говорит «не могу открыть» (честно, но бесполезно), или считает «что если» без кода. Машинные проверки это ловят — см. отчёт.
* Остановка хода хранится в памяти процесса (`ACTIVE_TURNS`). При нескольких воркерах uvicorn её нужно перенести в Redis pub/sub.
* Варианты написания поставщика (`suppliers.aliases`) пока задаются только в данных (сид), без экрана в интерфейсе.
* Маскирование имён — правила (основа слова, окончания, контекст), а не морфологический разбор: редкие формы и опечатки могут не узнаться. Для файлов это закрыто белым списком (в песочницу уходит только пересобранное содержимое), для свободного текста — нет.
* Нет списания брака у уже принятой партии, редактирования рецептов из UI и ручного ввода курса.
* Дополнительные задачи (pgvector, голос, Excel-экспорт, Playwright + CI) не делались, приоритет был у основных частей.
