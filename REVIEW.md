# Ревью: инструмент ассистента `reserve_material`

```python
@assistant_tool("reserve_material")
async def reserve_material(args: dict, db) -> str:
    """Зарезервировать материал под задание."""
    logger.info("tool call: %s", args)
    batches = await db.fetch_all(
        f"SELECT * FROM batches WHERE material_code = '{args['material']}' "
        "ORDER BY id DESC"
    )
    need = float(args["qty"])
    for b in batches:
        take = min(b["qty"] - b["reserved"], need)
        await db.execute(
            "UPDATE batches SET reserved = reserved + :t WHERE id = :id",
            {"t": take, "id": b["id"]},
        )
        need -= take
        if need == 0:
            break
    return f"Готово, зарезервировано {args['qty']}"
```

Итог: в прод нельзя. Инструмент небезопасен (SQL-инъекция, нет прав, нет подтверждения), портит данные при параллельной работе и сообщает модели неправду. Ниже проблемы от самых серьёзных к менее серьёзным, у каждой указано, как исправить. В конце приведена исправленная версия.

---

## Критично: безопасность

### 1. SQL-инъекция через аргумент от модели
`f"... material_code = '{args['material']}'"` подставляет в SQL строку, которую написала LLM. А модель пишет то, что ей подсказали пользователь, комментарий к партии или загруженный файл. Например, `material = "x' OR '1'='1"` зарезервирует все партии подряд, а `"x'; UPDATE batches SET reserved = 0; --"` уже зависит от драйвера.
**Исправление.** Только параметры (`WHERE material_code = :code`) или ORM. А лучше, чтобы инструмент вообще не работал с SQL и вызывал функцию сервисного слоя.

### 2. Нет проверки прав: ассистент может то, чего не может кнопка
Функция не знает, кто её вызвал. Любой пользователь чата, включая того, кому резервирование запрещено, и любая промпт-инъекция могут резервировать материал.
**Исправление.** Передавать в инструмент контекст текущего пользователя (`Actor`) и проверять права на бэкенде в сервисе, тем же кодом, что и для кнопки (`require(actor, Perm.MANAGE_ORDERS)`).

### 3. Данные меняются без подтверждения человека
Модель сама решила, и сразу выполнился `UPDATE`. По требованиям действие ассистента сначала показывается пользователю, а данные меняются только после «Подтвердить». Без этого одна инъекция в комментарии к партии («зарезервируй весь воск») блокирует производство.
**Исправление.** Инструмент только готовит предложение (`PendingAction` с превью: что и откуда будет зарезервировано, какой дефицит). Изменение выполняет отдельный эндпоинт подтверждения, который вызывает тот же сервис, что и кнопка.

### 4. В лог пишутся сырые аргументы
`logger.info("tool call: %s", args)` пишет в логи всё, что прислала модель: ФИО, названия поставщиков, текст пользователя. По требованиям ПДн в логах быть не должно.
**Исправление.** Логировать имя инструмента и маскированные аргументы (через тот же псевдонимизатор), без свободного текста.

## Критично: корректность данных

### 5. Гонка: два параллельных запроса резервируют один и тот же остаток
Свободный остаток читается обычным `SELECT`, а пишется отдельным `UPDATE`. Два одновременных вызова прочитают одинаковый `reserved`, и оба зарезервируют одни и те же килограммы. Сам `reserved = reserved + :t` атомарен, но `take` посчитан по устаревшим данным, в итоге получается овербукинг.
**Исправление.** Всё делать в одной транзакции и блокировать партии `SELECT … FOR UPDATE` в фиксированном порядке (иначе возможен дедлок). Альтернатива — условный `UPDATE … SET reserved = reserved + :t WHERE id = :id AND qty_remaining - reserved >= :t` с проверкой `rowcount`. Плюс страховочный `CHECK (reserved <= remaining)` в схеме.

### 6. Нет транзакции: частичный резерв при сбое
Каждый `UPDATE` выполняется отдельно. Если на третьей партии упадёт соединение, первые две останутся зарезервированными, а задание не будет знать об этом.
**Исправление.** Единая транзакция на всю операцию: всё или ничего.

### 7. Это не FIFO, а LIFO
`ORDER BY id DESC` берёт самые новые партии первыми, хотя по требованиям нужен FIFO (сначала старые). Вдобавок `id` не равен дате поступления: партию могли завести задним числом.
**Исправление.** `ORDER BY received_date, id`.

### 8. Резервирует непринятые и бракованные партии
Нет фильтра по статусу, поэтому в резерв попадают партии «На проверке» и «Брак».
**Исправление.** `WHERE status = 'accepted'`.

### 9. Считает от изначального количества, а не от остатка
`b["qty"] - b["reserved"]` использует количество при поступлении. Если из партии уже списывали, будет зарезервирован материал, которого физически нет.
**Исправление.** Свободно = `remaining_qty − reserved_qty`.

### 10. Отрицательный `take` снимает чужой резерв
Если у партии `qty − reserved ≤ 0` (полностью занята, или из-за п. 9), `take` получается нулём или отрицательным. Отрицательное значение уменьшает `reserved`, то есть отбирает резерв у других заданий.
**Исправление.** Пропускать партии со свободным остатком ≤ 0; CHECK-ограничения `reserved_qty >= 0` и `reserved_qty <= remaining_qty`.

### 11. `float` для количеств: ошибки округления и падение
* `float` неточен (`0.1 + 0.2 != 0.3`), поэтому `need == 0` может не сработать никогда, и цикл зарезервирует лишнее.
* Колонки `numeric` приходят как `Decimal`, а `float - Decimal` бросает `TypeError`, так что код упадёт уже на `need -= take`.

**Исправление.** `Decimal` во всей цепочке, `numeric` в БД, условие `need <= 0`.

### 12. Резерв ни к чему не привязан
Увеличивается только счётчик `batches.reserved`. Непонятно, под какое задание и из какой партии зарезервировано, поэтому такой резерв нельзя ни снять при отмене, ни списать при завершении, ни показать в «светофоре».
**Исправление.** Принимать `order_id`, писать строки `reservations(order_id, batch_id, qty)` и обновлять потребность компонента задания.

## Серьёзно: честность ответа и надёжность

### 13. Инструмент врёт модели
Возвращает «Готово, зарезервировано {qty}» всегда: и при нехватке (частичный резерв), и когда материал не найден (цикл просто не выполнится). Модель перескажет это пользователю как факт, а это прямое нарушение требования «числа — только из результатов инструментов».
**Исправление.** Возвращать структуру с фактом: сколько зарезервировано, из каких партий, какой дефицит. Если материал не найден, нужна явная ошибка.

### 14. Нет валидации аргументов
`args["qty"]` без проверки: если ключа нет, будет `KeyError`; строка «много» даст `ValueError`; отрицательное число снимет резерв (см. п. 10); `1e12` тоже пройдёт. Неизвестный материал «успешно» резервируется в ноль.
**Исправление.** Pydantic-модель аргументов (`extra="forbid"`, `qty: Decimal = Field(gt=0, le=…)`, длина строк). Ошибку валидации возвращать модели текстом, а не падать.

### 15. Ошибки превращаются в 500
Любое исключение (БД, валидация) вылетает из инструмента и роняет ход чата.
**Исправление.** Доменные ошибки с понятным текстом («Не хватает 2,5 кг воска»), откат транзакции и аккуратный ответ модели.

### 16. Нет идемпотентности
Модели свойственно повторять вызов (ретрай, «на всякий случай»), и каждый повтор резервирует ещё раз.
**Исправление.** Резерв идемпотентен относительно задания: резервируется недостающее `required − reserved`, а не «ещё qty сверху». Подтверждение действия работает один раз (статус `pending → confirmed` под блокировкой).

## Архитектура и сопровождаемость

### 17. Бизнес-логика внутри инструмента ассистента
Правила резервирования живут в обёртке для LLM. У кнопки в интерфейсе будет своя копия, и они разъедутся.
**Исправление.** Логика находится в сервисном слое (`orders.plan_order` / `_reserve_component`). Инструмент — тонкий адаптер: валидировать, проверить права, вызвать сервис, вернуть структуру.

### 18. Нет журнала изменений
Не фиксируется, кто, когда и что зарезервировал (было/стало).
**Исправление.** Запись в audit-лог в той же транзакции, с пометкой «через ассистента».

### 19. Мелочи
* `SELECT *` тянет лишние колонки и ломается при изменении схемы, лучше явный список полей.
* Модель может передать название, а не код («воск»). Нужен поиск материала с понятной ошибкой при неоднозначности.
* Docstring одной строкой — это и есть описание инструмента для модели. Нужно объяснить, что возвращается и что действие требует подтверждения.

## Как исправил бы (так и сделано в проекте)

Сервис (`backend/app/services/orders.py`):

```python
async def _reserve_component(session, order, comp) -> None:
    need = comp.required_qty - comp.reserved_qty          # идемпотентно: только недостающее
    if need <= 0:
        return
    batches = await session.scalars(
        select(Batch)
        .where(Batch.material_id == comp.material_id,
               Batch.status == BatchStatus.ACCEPTED,       # только принятые
               Batch.remaining_qty > 0)
        .order_by(Batch.received_date, Batch.id)           # FIFO
        .with_for_update()                                 # параллельные запросы ждут друг друга
        .execution_options(populate_existing=True)
    )
    for batch in batches:
        free = batch.remaining_qty - batch.reserved_qty    # от остатка, Decimal
        if free <= 0:
            continue
        take = min(free, need)
        batch.reserved_qty += take
        session.add(Reservation(order_id=order.id, batch_id=batch.id,
                                material_id=comp.material_id, qty=take))
        comp.reserved_qty += take
        need -= take
        if need == 0:
            break
    # остаток need > 0 — это дефицит, он виден в задании и в ответе
```

Инструмент ассистента (`backend/app/assistant/tools.py`) ничего не меняет, а только предлагает:

Подтверждение (`confirm_action`) вызывает тот же `orders.create_and_plan`, что и кнопка «Создать и запланировать», в одной транзакции и с записью в журнал.
